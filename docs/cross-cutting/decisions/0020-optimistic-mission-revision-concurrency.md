# 0020. Optimistic Mission Revision Concurrency: `client_version` For Mutation, `controller_version` For Cutover

Date: 2026-05-26
Status: Accepted

## Context

Mission revisions can be edited by the operator (through the map widget), regenerated by the planning shell, and executed against an external controller. Each of these can race the others:

- Two browser tabs (or two operators) editing the same revision can interleave mutations.
- The AI planner can regenerate a draft while the operator is editing it.
- Execution cutover can race a new revision becoming the active one.

Pessimistic locking (server-held edit locks) is heavy and breaks down when a client crashes mid-edit. Last-write-wins silently loses work and silently flies wrong missions.

## Decision

Two optimistic concurrency controls protect mission state:

1. **`client_version` guards revision mutation.** Each revision carries a monotonically incremented version that bumps on every waypoint mutation. Mutation requests must target the latest known `client_version`; stale requests are rejected and the client is expected to refresh and retry against fresh state.
2. **`controller_version` guards execution cutover.** Execution checks the expected live controller mission version before install and read-back. A mismatch rejects the cutover; the system creates a rebased `awaiting_approval` revision against the latest verified controller state so the operator can re-review.

## Consequences

- Stale edits fail loudly at the backend boundary instead of silently overwriting newer state.
- Stale execution cutovers fail loudly and produce a rebased review revision rather than installing a mission against unexpected controller state.
- Clients (map widget, planning shell) must handle stale-version rejections by refreshing and re-presenting state, not by retrying blindly.
- Audit trails are preserved: the execution attempt log records expected vs. observed vs. installed versions per attempt.
- No server-held locks means a crashed client never leaves the system in a stuck state.

## Alternatives Considered

- **Server-held edit locks.** Rejected: brittle under client crashes; adds a lifecycle that has to be cleaned up.
- **Last-write-wins.** Rejected: silently destroys operator edits and can install a controller mission that was never reviewed against the current live state.
- **Single version for both mutation and cutover.** Rejected: conflates client-side edit ordering with controller-side mission identity. They have different failure semantics and different rebase strategies.
